## 二、按开发顺序交接实现

### 1. 打通订单 A/B 首条链

**T01** 从 Maven 模块和两个 Spring Boot 启动入口开始。装配 Spring MVC、`JdbcClient`、事务、Flyway 和 Actuator，分离管理写入和 `runtime-auth` 读权限。先冻结 `integration-contracts` 的 `SourceAdapter`、`ResourceHandler`、`ProtocolTargetResolver`，及 `authorization-core` 的 `PolicyEvaluator`、凭证只读视图、决策/事件字段。底层提供数据库初始化、开发配置及可启动的管理应用和运行桥；各业务表及写入规则由对应模块交付。调用方可以据此并行接实现。

**T06** 可与应用骨架并行，由网关/环境负责人在实际镜像上验证 Console GET 权限、External Auth、`allowed_properties` 的实际 `route_name`、部署修订、Key 剥离、信任头覆盖、短时证明及故障拒绝。先用隔离探测路由和受控鉴权回执验证，不依赖正式订单发布。交付镜像/插件版本、路由配置、实测字段和入口可用结论。LLM 实际目标和 MCP 会话转发的专项探测随 T21/T22，各自通过后才开放对应入口。现成插件链能力不足时按架构使用受控执行适配或保持对应入口未发布。

**T09** 从 `governance-domain` 的账号、平台资格、外部账号映射、角色/组织关系和指派开始，接 `management-authz` 的 `ManagementAuthorizer.check(actor, operation, objectScope)`。复用 Spring Security 方法拦截，在管理应用服务核对会话和平台、对象、应用委派，并将检查与写入放在同一事务边界；同步外部状态与本地状态独立，企业应用使用自己的账号。依赖 T01。首条链先提供天机身份和目录发布、签发所需服务端检查，后续操作在各业务任务中接入同一入口。真实岗位、跨平台授权和自批例外仍需明确委派，开发用隔离模拟岗位，无委派默认拒绝。

**T02** 从连接注册和同步作业入口接 `SourceAdapter` Bean，先支持天机全量的最小提交。复用 `TaskScheduler/TaskExecutor`、JDBC 事务和 PostgreSQL 的行级作业领取。Adapter 拉外部页，`source-sync` 按运行与页位置暂存，验证完整性后将来源事实、`committedCheckpoint`、审计和 outbox 同事务提交。公共管线负责增量/全量衔接、重试、租约接管、旧持有者隔离和事件重放，并提供手动同步和运行状态查询；来源协议留给 Adapter。依赖 T01 与 T09 的事实写入接口。首条 HTTP 只依赖一次完整基线可提交，T05 使用同一入口验收扩展和接管。

**T03** 按 §2.1、§5.4 的暂定外部协议在独立进程提供天机登录交换、快照/增量、模拟变更通知和 `/internal/orders/{orderId}`。Mock 持有外部身份、指派和订单关系夹具，校验受信链路及上游证明后以外部身份判 A/B，输出关联请求与尝试的业务回执。与 T04、T20 先对齐协议和证据字段，交付可独立部署的服务和固定数据，无需等待真实天机接口，也不写治理主库。

**T23** 从统一事件结构与现有日志接入点开始。先发布管理变更、`DecisionEvent`、`AttemptEvent`、`UsageEvent` 契约，管理写入随本地事务留痕，授权桥提供判定和原因，网关/代理提供实际尝试，上游提供确认回执。依赖 T01 的事件契约，可先交付写入与按 `requestId/attemptId` 关联的最小查询或看板，供 T08、T15、T20 接入。HTTP 链验收时能区分平台拒绝、已转发且业务拒绝、实际成功；采集与审计不落 Key 明文、Prompt、Completion 或工具参数。

**T07** 从 `catalog-higress`、后台网关连接配置和 `POST /admin/catalog/refresh` 开始，用 `RestClient` 接 Console `/v1/routes`、`/v1/ai/routes`、`/v1/ai/providers`、`/v1/mcpServer` 及必要插件实例 GET。HiMarket `HigressClient` 和 `HigressOperator` 仅供参考会话、分页和协议。读账号不足以限制时用受控路径白名单；会话登录仅用于建立 Console 会话，资源配置由网关管理员维护。依赖 T01、T06 的实际连接配置和 T09 管理权限。先提交去重 HTTP 候选及刷新状态，其余类型复用同一连接与候选契约。

**T08** 从资源 `publish/suspend/retire` 接入 `ResourceHandler.validateBinding`。把只读候选、受控部署的路由证据与业务资源 ID 绑定，写入发布状态、实际路由、修订和操作审计。在运行端提供按绑定及状态读取的稳定视图，供授权桥硬校验；相同发布接口可扩展模型、Server/Tool。首条 HTTP 发布依赖 T06 对该入口的证据、T07 候选、T09 委派和 T23 管理事件接口。发布不依赖订单已验收；模型和 MCP 的实际入口发布分别等各自协议执行证据。

**T04** 从 `source-tianji` 的 `exchangeIdentity`、`pull/normalize` 接入，复用 `RestClient` 和 T02 的注册、暂存、提交入口。把 Mock 的稳定外部账号、角色与指派标识、外部资源和授权转换为平台命名空间内的事实，保留运行时可反查的外部身份映射；模拟通知校验来源后只触发拉取。依赖 T02、T03、T09 与 T01 的目录映射契约。来源先落可重放的外部记录；目录绑定可用后继续解析映射，无法解析的记录按设计隔离。首条 Key 签发前，订单资源映射和账号授权须已提交生效。

**T16** 在 `policy-reference` 实现 T01 的 `PolicyEvaluator`，从治理事实快照按 v1.6 固定规则求值。同层拒绝优先，适用本地规则覆盖外部基线，无许可默认拒绝。预留并消费统一的本地规则/基线视图；首链用 T04 的已提交基线，审批和覆盖接口随后提供同视图的数据，无需替换求值器。依赖 T01、T09 的身份和事实读契约，向 T15 交付直接授权 A 的可部署装配。

**T15** 从 `runtime-auth` 的 `/internal/preview`、`/internal/ext-auth/{routeBindingId}` 及后续代理 `/internal/authorize` 开始。先交付预览和硬校验，读取 T08 发布/绑定、T09 身份及 T16 求值结果，并向 T10 提供无 Key 的身份权限预检。运行路径通过 T01 的凭证只读接口核验 Key 摘要、版本、状态和精确 Scope，在同一事实快照中将硬检查与 `PolicyEvaluator` 决定合并。面向 HTTP 签发限定上游和对象的 `UpstreamProof`，面向 MCP 签发限定代理和本次请求的 `EntryProof`；原始 Key 只经过客户端、Higress 和授权桥，后续交接使用短时证明。挂接 T23 决策事件。运行阶段与 T10 合装，预检接口可先独立交付。

**T10** 从 `GET /key-options`、`POST /keys` 接 T15 预检及 T09 委派。事务内校验当前有效身份、已发布目标和精确动作，保存与平台/角色指派绑定的 `ApiKey`、摘要和 `KeyScope`，只在签发成功时展示明文。实现 T01 的凭证只读接口供授权桥运行路径读取。依赖 T04 的已解析授权基线、T08 已发布订单资源和 T15 预览；不依赖审批、覆盖或完整生命周期接口。交付仅勾选订单查询的 Key 与可区分范围缺失的请求结果。

**T20** 从可信 `routeBindingId`、部署修订及实际 Method/路径进入 HTTP Resolver，沿用 T06 验证过的 External Auth 配置，将真实命中映射到 T08 订单权限。联通 T15/A、T10、T03：桥将 T04 映射出的外部身份写入绑定订单对象和单次尝试的证明，由 Higress 清除原 Key 后转给 Mock。Mock 对对象 A/B 作最终决定，T23 用请求和尝试 ID 关联两层审计。交付首条可部署入口及 E1 的联调记录，作为后续两协议接入和 A/B 对比的共用基线。

### 2. 接续治理功能、协议和运营

**T05** 从新 `SourceAdapter` Bean 和来源 B 的连接配置起步，只交付 B 的认证、分页、快照覆盖证明、组织成员和授权映射。依赖 T02 的公共作业、T09 平台/组织事实和 T08 规范目标，复用同一游标、隔离和事务提交；组织来源不生成业务角色。同名角色隔离用单独的角色型跨平台夹具核验，保持 B 的组织身份语义。交付 B 的成功同步与中断后接管记录供维护者对照。

**T11** 从 `PUT /admin/overrides/{id}`、指派停启和策略预览入口扩展治理规则服务。将来源基线和本地规则独立写入与展示，允许、拒绝、恢复交给共同规则视图；同步保留本地覆盖，身份停用通过 T15 硬门槛影响已签发 Key。依赖 T02、T09、T16、T23，向 T12 提供带审批引用的受限本地授权写入口。平台权限管理员在明确委派范围内操作，覆盖和停启 API 的越权验收随交付。

**T12** 从 `/model-applications` 和审批决定入口接 T09 管理授权、T08 模型目录、T11 本地规则写入口。通过时同事务写审批记录、申请身份限定规则、事件和版本，审批后授权候选进入 T15/T10 的预览，原 Key 范围仍需要用户显式勾选。未授权岗位及自批例外默认拒绝，审批 API 的越权验收随交付。模型目录可先提供已核验的验收绑定，正式模型路由开放依赖 T21 的实测证据。

**T13** 从 Key 列表、`PUT /keys/{id}/scope`、`rotate/revoke` 延续 T10 的存储及响应契约。范围修改复用同一预检，仅更新当前 Key 的条目和版本；轮换保留范围并使旧凭证失效，到期和吊销立即通过 T15 的当前事实检查拒绝。依赖 T09 的个人/应用委派、T10、T15 和 T23。覆盖应用 Key 的直接 API 越权和变更审计，向页面供给状态、范围及一次展示能力。

**T21** 从 LLM `ProtocolTargetResolver` 接 T07 的 AI 路由/Provider 候选和 T08 的发布绑定。复用 Higress External Auth 和 `ai-proxy`，从受限请求体解析模型别名、识别并锁定出站 Provider 和实际模型；共享入口上按实际模型单独授权，使用 T15 的等同判定，跨模型回退首期关闭。依赖 T06、T07、T08、T15 和 T23；使用真实路由确认目标与供应商凭据隔离后再发布。向 T24 输出请求和实际模型、调用尝试及流式 Usage，端到端模型审批和旧 Key 显式勾选在 T12/T13 就绪后验收。

**T22** 从 MCP `ResourceHandler`、真实 Higress 的 Server 入口及 `mcp-auth-proxy` 接入。T07 导入或补齐真实 Server 和工具清单，T08 分别登记 Server 和 Tool。代理接 T15 `EntryProof` 与逐消息判定，按 `discover` 过滤 `tools/list`，对 `tools/call` 解析当前会话和 Tool 重新判 `invoke`；撤权后已初始化会话的直调同样受限。经受信私网到 Higress 托管工具或已有 MCP 服务，用同一代理执行边界。依赖 T06、T07、T08、T15 和 T23；托管与代理模式分别据实测开放，向用量侧输出拒绝、执行尝试、业务结果和执行未知。

**T24** 从 T23 的事件消费和现有日志/看板接口开始。复用 Higress AI Statistics 与 `wasm.ai_log` 的可核验字段，按请求和尝试关联 T21 的实际模型与输入/输出 Token，流中断或缺 Usage 标记不完整。接 T22 的 `tools/call`，按确认发起执行统计尝试，单独保留鉴权拒绝和未确认回执。消费按 `eventId` 去重。依赖 T09 委派、T20/T21/T22 事件及 T23，提供按平台、账号、应用、Key、角色/组织、模型或工具查询聚合，审计读取与导出受相同范围控制。交付给 T14 看板入口和 T25 额度聚合。

**T14** 从现有前端宿主开始，各页面跟随 API 交付。T02/T04/T09/T07/T08 提供身份同步、目录和只读网关连接设置；T11、T12、T10/T13 分别提供覆盖、审批和凭证页面；T23/T24 提供审计入口与现有用量看板。页面读取服务端授权范围并呈现真实数据，禁止通过页面逻辑取代服务端检查。先对接隔离岗位，正式岗位配置等待业务委派；首条 HTTP 链可先用 API 完成，页面按同一契约验收。

**T25** 从已提交的用量聚合和事件状态配置用户/组织软额度、告警和看板，达到额度继续执行；网关限流沿用实际部署配置。依赖 T02、T15、T23、T24 和现有告警工具，在看板展示同步滞后、授权耗时与拒绝原因、上游失败及用量缺口，并交付授权服务不可用、审计/用量积压和额度超阈等告警的定位与处置说明。B1 模式另接 T18 提供的传播水位、装载失败告警；A 的共用运维无需等待 B1。具体阈值由运营确认。

### 3. 并行验证 B1，决定是否采用

**T17** T01 的策略/事实契约和 T02 的事务 outbox 可供消费后，在本地 `policy-ranger` 并行对接 Ranger Admin 的公开 `ServiceREST` 和 `RangerAdminRESTClient`。将业务事实按平台投影到 `enterprise_access` ServiceDef，按外部基线与本地覆盖映射原生优先级，完整读回校验后封存 `P/V` 工件并关联规则来源。可证明纯增权推进目标代际，限制性或不确定策略变化同步提高 `requiredPolicyG`，直接事实失效仍交给硬检查。最初用共同夹具即可开始，实际对比读 T08/T09/T11 的同一事实契约；交付可供 T18 安装的完整工件和水位状态。

**T18** 在 T15 共享 `PolicyEvaluator` 边界上接 T17。关闭 Ranger 原生自动刷新，用公开 `RangerBasePlugin.init/setPolicies/getPolicyVersion/cleanup` 装载封存工件，原子切换活动实例及 `Vi`，按当前平台安全水位及 epoch 判断是否能服务，新增实例达到已发布服务代际 `servingPolicyG` 后才承接对应流量。纯增权可沿用已证安全的旧代际，撤权或混合变更抬高安全水位后，装载失败且旧代际低于水位时关闭受影响分区的旧求值。交付实例就绪/传播状态、受控模式切换及回到 A 的配置，供 T19、T25 消费；与主应用事实及网关适配保持同一接口。

**T19** 自 T17/T18 开始记录复用与新增职责，完成报告依赖可部署 A、实际 HTTP/LLM/MCP 路径和同一治理事实。按架构 §9.3 同场景实测 A/B1：提交同平台无关流量阻断范围、持续时间、撤权与恢复结果、错误放行情况、第二真实调用方复用及装载运维成本。业务方裁决是否接受同平台 `503` 并明确中断预算和切换阈值；未确认或未通过验收即保持 A。为已验证 A 准备受控回退步骤并记录最终采用结论。B1 采用仅是条件分支，不阻塞共用能力验收。
